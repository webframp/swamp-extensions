### [MEDIUM] Both new resources write under the same data name
**File:** gitlab/extensions/models/gitlab/projects.ts
**Line(s):** ~4386 (`workItemParent`), ~4471 (`workItemType`)
**Issue:** Both methods write `${sanitizeName(project)}-work-item-${iid}`. Swamp keys data by data name per model: `data.latest(model, name)` takes only the name, and the spec is just a tag. The two specs therefore share one version history.
**Breaking input:** Run `remove_work_item_parent` on `group/proj` iid 7, then `convert_work_item_type` on the same item.
**Impact:** `swamp data get gitlab group~proj-work-item-7` and `data.latest(...)` return whichever spec was written last, and the version history mixes the two schemas. CEL that expects `previousParent` can get a `workItemType` record. The siblings `issueAssignees`, `issueDiscussions` and `notes` already share `-issue-&lt;iid&gt;`, but this branch adds a new collision.
**Fix:** Use `-work-item-${iid}-parent` and `-work-item-${iid}-type`.

### [MEDIUM] A parent the caller cannot read is reported as "no parent"
**File:** gitlab/extensions/models/gitlab/projects.ts
**Line(s):** WORK_ITEM_QUERY (~1877), `workItemParentRef` (~1920), `if (previousParent)` (~4357)
**Issue:** GitLab authorizes `WorkItem` objects per field. If the parent is confidential or sits in a project the token cannot read, `hierarchy.parent` comes back `null` even though the link exists. The code treats `null` as "no parent", skips the mutation and records `previousParent: null`. `WorkItemWidgetHierarchy.hasParent: Boolean!` exists to tell these cases apart.
**Breaking input:** The lookup returns `widgets: [{ parent: null, hasParent: true }]`.
**Impact:** The method logs "Work item #7 has no parent", writes a resource saying so, and returns success while the item is still attached. The release note's "no-op when already in the requested state" claim is false here.
**Fix:** Select `hasParent` in the lookup and in the mutation response. Mutate when `hasParent` is true. If the parent reference is null but `hasParent` is true, record a placeholder or throw.

### [MEDIUM] `remove_work_item_parent` treats an empty mutation response as success
**File:** gitlab/extensions/models/gitlab/projects.ts
**Line(s):** ~4375–4381
**Issue:** `parent = workItemParentRef(result.workItem)` returns `null` when `result.workItem` is null or when the hierarchy widget is missing. The check `if (parent) throw` passes in both cases, so the method writes `parent: null` as confirmed. `convert_work_item_type` throws on the equivalent case ("returned no work item type"), so the two new methods are inconsistent. The "GitLab kept parent" check only catches a widget that is present and non-null; it cannot detect a missing confirmation.

**Impact:** A detach that did not happen is recorded as done.
**Fix:** Throw when `result.workItem` is missing or has no hierarchy widget. Better, check `hasParent === false` in the response (see the previous finding). Add a test for each case.
