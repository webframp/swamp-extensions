## What changed

**1. README.** Every README now has the canonical Credentials section: `swamp vault create local_encryption datadog`, then `swamp vault put datadog API_KEY` and `APP_KEY`. The usage example now uses `--global-arg 'apiKey=REDACTED vault.get("datadog", "API_KEY") }}'` and the same for `appKey`. The old `DD_API_KEY`/`DD_APP_KEY` literals are gone; swamp rejects literal values for sensitive global arguments anyway.

**2. Argument descriptions.** `apiKey` and `appKey` were already marked sensitive; their descriptions now say to wire them with `vault.get` and never pass the literal value. The generator has no environment-variable fallback, so there was nothing to downgrade.

**3. Secret-valued method arguments.** A new name matcher (`lib/sensitive.ts`) marks credential-named fields sensitive, including nested request-body fields. Its tests also check it does not catch look-alikes such as `author`, `creationAuthorId`, `session_id`, `cert`, `api_key_id`, `page_token`, `max_tokens` and `has_password`. On the pinned spec it marks no Datadog argument at all. Arguments whose name gives no hint are listed in a new `SENSITIVE_ARG_FIELDS` map in `config.ts`, which currently holds `PatchGlobalVariable.json_patch`: a patch that sets a global variable's value carries that secret.

**4. Secrets in API responses.** I scanned every request, parameter and response schema of the 165 operations, resolving references fully. No create or action returns an API key, application key, token or webhook secret; the only credential-like names were public certificate fields, RUM `session_id` and author IDs. The response fields that do carry secrets are all in synthetics, listed in a new `SENSITIVE_RESPONSE_FIELDS` map and marked sensitive so swamp stores them in a vault:
- `patch_global_variable` → `value.value` (a global variable's value, which Datadog returns unless the variable is flagged `secure`)
- `get_test_file_download_url` → `url` (presigned URL)
- `get_test_file_multipart_presigned_urls` → `multipart_presigned_urls_params` (presigned upload URLs)

Generation now fails if a listed field is missing from the schema, or if a secret sits inside an array, record or union, where swamp does not vault resource fields. That stops API drift from silently dropping the protection.

**Tests.** The generator has 14 new tests. Every generated extension now checks that both keys are marked sensitive. Synthetics also checks the `json_patch` marking and plants a sentinel secret in each of the three responses, then asserts no plaintext is left once the marked paths are replaced. The test context does not vault anything itself, so that last step stands in for swamp's data writer.

## Behavior change for synthetics users
Once a model declares sensitive output, swamp refuses to run any of its methods, reads included, until a vault exists. Synthetics method names never match swamp's read/list names, so all 35 methods are affected. The README and release notes say this.

## Calls you may want to reverse
- **Presigned URLs treated as secrets:** they are short-lived bearer URLs, so this is a judgement call.
- **`value.value` treated as a secret:** Datadog only returns it for variables not flagged `secure`.
- **`json_patch` marked sensitive:** swamp masks every string in the patch in output, including words like `replace` and paths like `/name`, not just the secret.
