### Is retrying a write on 503 + Retry-After safe?
Yes; the risk is low and the change is acceptable. The duplicate-write risk comes from responses sent after the backend has already committed:
- **Gateway timeouts after the backend committed:** Heroku H12 sends 503, ALB and nginx send 504, Envoy sends 503 on an upstream reset. None of these add `Retry-After` by default.
- **Responders that do send `Retry-After`:** throttles such as Rack::Attack (which sends 429 anyway), maintenance pages, and HAProxy or Apache when no backend is available. All of these answer before Redmine runs.
- **Redmine itself:** Rails/Puma does not send 503 with `Retry-After` from inside a request.

So the header is a good sign that no work was done. The cost is the uncapped delay in the MEDIUM finding below.

### [MEDIUM] Retry-After is uncapped, so one method can hang for hours or days
**File:** `redmine/extensions/models/redmine/_lib/api.ts`
**Line(s):** 28–35 (`retryDelayMs`) and 150–153
**Issue:** `Number(retryAfter) * 1000` is passed straight to `setTimeout` with no ceiling. In Deno I confirmed:
- `86400` sleeps a full day.
- Values above 2^31−1 ms (about 24.8 days), `Infinity` and negative values all fire after about 1 ms, so the request is retried almost at once.
- An HTTP-date value is NaN and falls back to backoff of 1, 2, 4 and 8 seconds, which ignores the date.

**Breaking input:** A maintenance responder sending `503` with `Retry-After: 3600` blocks any method, writes included, for 4 hours (4 retries). With `86400` it blocks for 4 days.
**Impact:** A workflow hangs silently. The README and release notes tell users requests "time out after 120 seconds per attempt", but the sleep between attempts has no bound. The parsing was the same on main, where a 503 already retried for every method. This branch rewrote this retry loop and now documents bounded deadlines, so per your rule on defects that share a root cause, it is in scope.
**Fix:** Cap the delay (for example 60 s). When `Retry-After` exceeds the cap, return the response without retrying. Parse the HTTP-date form with `Date.parse(v) - Date.now()`, and treat a negative or non-finite value as backoff. Add a test where a large `Retry-After` is not slept on.
