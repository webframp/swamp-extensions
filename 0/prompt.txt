### [MEDIUM] Removing a parent the token cannot read: GitLab refuses it, but the README, release notes and a test say it works
**File:** `gitlab/README.md` (work item caveats section), `gitlab/RELEASE_NOTES.md`, `gitlab/extensions/models/gitlab/projects.ts` (`WorkItemParentSchema.previousParent` description), `gitlab/extensions/models/gitlab/projects_test.ts` (test "detaches a parent the token cannot read")
**Line(s):** README ~238-241; RELEASE_NOTES lines 8-11; projects.ts ~438-440
**Issue:** All three claim that a parent the token cannot read is found through `hasParent` "and removed". GitLab's code does not allow that. Sending `parentId: null` ends up in `WorkItems::ParentLinks::DestroyService#permission_to_remove_relation?`, which requires both:
- `can?(current_user, :admin_parent_link, child)`
- `can?(current_user, :admin_parent_link, parent)`

A token that cannot read the parent cannot administer it either. GitLab returns the error `"No Work Item Link found"`, which the method throws as `workItemUpdate failed: No Work Item Link found`.

So the iteration-1 `hasParent` fix only half-works. It now detects the hidden parent, which is good: the method no longer reports "no parent", and the failure is loud. But the success path the docs describe, a resource with `hadParent: true` and `previousParent: null`, can't happen in real use. The test asserts that path with a mocked success that GitLab never returns.
**Breaking input:** Child in project A; parent is a confidential issue, or sits in project B, which the token cannot see.
**Impact:** Users are promised a capability that doesn't exist. The error they get ("No Work Item Link found") is misleading, because a link does exist.
**Fix:**
- Rewrite the README and release-note bullets: a hidden parent is detected, and the method fails because GitLab requires access to the parent.
- When `before.hasParent &amp;&amp; before.parent === null`, either throw before the mutation with a clear message ("work item has a parent this token cannot read or administer"), or add that hint to the error GitLab returns.
- Change the test to match.

### [LOW] `hasParent` needs GitLab 17.2 or later; older instances reject the whole query
**File:** `gitlab/extensions/models/gitlab/projects.ts`
**Line(s):** `WORK_ITEM_QUERY` and `REMOVE_WORK_ITEM_PARENT_MUTATION` (~1880-1900)
**Issue:** I grepped GitLab's GraphQL reference at each release tag:
- `WorkItemWidgetHierarchy.hasParent` is absent at v16.0, v16.5, v17.0 and v17.1.
- It first appears at v17.2 and is present through v18.6 and master.
- The docs carry no "Introduced in" note for it, so the reference page alone hides the minimum version.

Every other field the queries use is much older: `Project.workItems` (15.1), `workItemConvert` (15.11), `workItemTypes`, and the `hierarchyWidget.parentId: null` input. Because `WORK_ITEM_QUERY` is shared, `convert_work_item_type` also fails on 17.1 and earlier, even though it never reads `hasParent`. That's the same failure mode as issue #476 (an unknown-field error).
**Breaking input:** Any self-managed GitLab at 17.1 or older.
**Impact:** Both methods fail with `Field 'hasParent' doesn't exist on type 'WorkItemWidgetHierarchy'`. In practice the exposure is small, since 17.x left security support long before October 2026.
**Fix:** State "requires GitLab 17.2+" in the README. Optionally, give convert its own query without the hierarchy fragment, so it works on older instances.
