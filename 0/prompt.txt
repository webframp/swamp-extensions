**Finding 2: limiter skipped on retries (line 552): works, but the trade-off is weaker than the comment and release note claim.**
- MEDIUM, `vertex_usage.ts:549-552` and `RELEASE_NOTES.md`: retries are invisible to the limiter, and Google counts them against quota. The comment says a second slot "would spend quota meant for projects not yet scanned". In fact the retry spends Google's quota in either case, and the fix only stops the limiter from counting it. The release note ("does not make the scan spend its per-minute budget twice") is accurate only about the local limiter.
  - The burst is bounded. At most `concurrency` requests are in flight, and `concurrency` is capped at 16. During a 5xx outage each worker sends up to 6 unlimited retries over about 31.5 seconds (backoffs of 0.5, 1, 2, 4, 8 and 16 seconds). With 16 workers that is up to about 96 extra requests in roughly 30 seconds. This is smaller than a continuous burst but similar in size to the 60-request headroom between the default limit of 120 and Google's 180.
  - A 429 retry waits at least 5 seconds, so that case is milder.
  - Users who set `maxRequestsPerMinute` between 180 and 6000 have no headroom at all.
  - Fix: record the retry in the window without waiting. For example, add a `record()` that pushes `nowFn()` onto `stamps` and call it on `attempt &gt; 0`. Later first attempts then see retries in the window, and retries are never blocked mid-backoff. Failing that, reword the comment and release note to say the limiter counts first attempts only.
- Alternative design: calling `limit()` on every attempt was the earlier behavior. It is conservative and correct for quota, and the cost is only extra waiting. The "record without waiting" option is better than either.
- Test (line ~2088): it fails without the fix. In my scratch copy with the `attempt === 0` guard removed, it failed with `assertEquals` at test line 2126 (`-2 +3`, `withRetry.monitoring` vs `baseline + 1`).
  - It is not flaky. `nowFn` is frozen at 0, the 429 backoff is 5000 ms against a 60000 ms threshold, and there is no Retry-After header, so there is no collision.
  - It restores state. It touches no env vars, and `sleeps` and `monitoring` are local to each call.
  - LOW: the test calls `execute` directly, which bypasses the zod `min(10)` on `maxRequestsPerMinute`. It passes `limit = 2`, which is fine today but would break if `execute` ever validated its arguments.
