### HIGH: PUTs that add data are still retried on 502/504, which duplicates journal notes
**File:** `redmine/extensions/models/redmine/_lib/api.ts` (lines 13-20); `redmine/extensions/models/redmine/redmine.ts` (`update_issue`'s PUT around line 1540; `upload_file`'s attach PUT around line 2527)
**Issue:** The PR limits POST retries to 429 because "a 502 or 504 can arrive after Redmine already created the record". That reasoning applies just as much to `PUT /issues/:id.json` with `notes`: every successful PUT creates a new journal entry. `isRetryableStatus` still retries PUT on 502/503/504, and both RELEASE_NOTES.md and the README now present this as correct ("GET, PUT and DELETE still retry 429/502/503/504").
**Breaking input:** Run `update_issue` with `notes: "deployed"`. Redmine saves the journal, then a proxy returns 504. The retry posts the note again, up to 4 duplicate comments in total.
**Impact:** Duplicate comments on real tickets. This is the same root cause the PR fixes for POST, so it falls under the user's in-scope rule.
**Fix:** Retry only on 429 for any method other than GET or HEAD. Alternatively, pass a per-call `idempotent` flag, so `update_journal` and `update_version` can keep 5xx retries while `update_issue` with notes and the upload attach step cannot. Correct the release notes and README to match, and add a test.

### MEDIUM: Retrying a DELETE after a 502/504 reports failure for a delete that succeeded
**File:** `_lib/api.ts` line 19
**Issue:** If Redmine deletes the issue, relation, version or watcher and a proxy then returns 502, the retry gets a 404 and `redmineApi` throws.
**Breaking input:** `delete_issue` when the gateway times out after the delete has committed.
**Impact:** The workflow step fails although the record is gone. A re-run fails again with 404.

### MEDIUM: Distinct inputs to the same method still overwrite each other's data
**File:** `redmine.ts` line 2068 (`search`) and lines 1884-1890 (`list_time_entries`)
**Issue:** CLAUDE.md requires instance names to be collision-resistant (hash variable inputs). The PR fixes overwrites across methods and claims every name is now safe, but overwrites within a method remain:
- `search` replaces every non-alphanumeric character and truncates to 50 characters, so `foo bar`, `foo-bar` and `foo_bar` all write `search-foo_bar`. Any two queries sharing their first 50 characters also collide.
- `list_time_entries` ignores `userId`, `from` and `to`, so different users and date ranges all write `time-entries-all` or `time-entries-&lt;project&gt;`.
- `issueId: 5` and `project: "5"` (a numeric project ID) both write `time-entries-5`.
**Impact:** A later run silently replaces data from different inputs. This is the overwrite defect the PR fixes, inside one method.
**Fix:** Append a short SHA-1 of the normalized arguments, for example `search-&lt;sanitized&gt;-&lt;hash8&gt;`, and include every filter in the time-entries name.
