### [MEDIUM] Keys from `list()` that contain the separator in a directory name cannot be read back with `get()` or written with `put()`
**File:** vault/pass/extensions/vaults/pass.ts
**Line(s):** `splitFieldSelector` / `assertSafeField` (about 222-247); `put` check (about 360-370)
**Issue:** The split happens at the last separator, and a field containing `/` is then rejected instead of being treated as part of the path. So an entry whose directory contains the separator is only reachable with a field selector; the entry itself can never be read. The code comment says a separator inside a directory name "still leaves the field at the end", which implies that case is supported, but only the field form works. `list()` still returns these keys, and they fail.
**Breaking input:** `fieldSeparator: "#"`, entry `swamp/team#a/entry`. `list()` returns `team#a/entry`. `get("team#a/entry")` throws `selects an invalid field: ... no '/' or ':'`, and `put("team#a/entry", v)` throws `cannot write a single field`. Also `list()` returns `a#` (entry `swamp/a#`), and `get("a#")` throws.
**Impact:** Keys from `swamp vault list-keys` fail in `read-secret` or in a vault expression. Existing entries become unreadable and unwritable as soon as `fieldSeparator` is turned on, and nothing warns about it.
**Fix:** When the text after the last separator contains `/`, treat the key as having no field. That makes the directory case round-trip and matches the code comment. Then decide about a trailing separator (`a#`): either fall back to the literal key or keep rejecting it, but say which in the README. A round-trip test is also missing.

### [MEDIUM] A separator that appears in an entry name silently returns another entry's value
**File:** vault/pass/extensions/vaults/pass.ts
**Line(s):** ConfigSchema `fieldSeparator` (about 204-206); `splitFieldSelector`
**Issue:** The schema blocks only `""` and anything containing `/`. Whitespace and other characters common in entry names are accepted. A key naming a real entry is then re-read as `&lt;other entry&gt;#&lt;field&gt;` and returns that other entry's field value, with no error.
**Breaking input:** `fieldSeparator: " "`, entries `swamp/my entry` and `swamp/my` (the latter containing `entry: wrong`). `get("my entry")` returns `"wrong"` from `swamp/my` (argv `["show","swamp/my"]`).
**Impact:** A consumer gets a different secret than the one it named, with nothing to show the read went wrong. The README tells users to choose a safe separator, but nothing enforces it.
**Fix:** At minimum, reject whitespace-only and whitespace-containing separators in the schema (a `\s` test in the refine) and add that config to `invalidConfigs`. Better, also fall back as in the first finding.

### [LOW] `#otpauth` and bare-URL lines are parsed as fields and return mangled values
**File:** vault/pass/extensions/vaults/pass.ts
**Line(s):** `extractField` (about 172-182)
**Issue:** Any line with a colon counts as a field, split at the first colon.
**Breaking input:** An entry line `otpauth://totp/a?secret=ABC`. `get("e#otpauth")` returns `"//totp/a?secret=ABC"`. A bare `https://x` line likewise answers `#https`.
**Impact:** pass-otp users who try `#otpauth` get a broken URI back with no error.
**Fix:** Require the field name to match `^[^\s:/]+$` and skip lines whose colon is followed by `//`, or say in the README that URI lines are not fields.

### [LOW] `put` and `get` record `vault.secret_key` differently when a selector is present
