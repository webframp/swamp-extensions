## Data Flow: IDs, Types, and Unsafe Patterns

### Issue IDs

**Evidence**: Issue IDs are plain JavaScript `number` throughout, passed directly without wrapper types.

- `/redmine/extensions/models/redmine/redmine.ts:1054` — `issueId: z.number().describe("Issue ID")` in `get_issue` arguments.
- `/redmine/extensions/models/redmine/redmine.ts:1193` — `issueId: z.number().describe("Issue ID to update")` in `update_issue`.
- `/redmine/extensions/models/redmine/redmine.ts:1321` — `issueId: z.number().describe("Issue ID to delete")` in `delete_issue`.

**Pattern**: Used consistently as `issueId` in method names and arguments. Stored in resource instance names as `String(args.issueId)`.

**Unsafe pattern**: Multiple numeric IDs (issueId, parentId, assignedToId, trackerId, statusId) can be passed to any method accepting a `number` argument without type safety distinguishing them:

```typescript
// redmine.ts:1400–1412
create_relation: {
  arguments: z.object({
    issueId: z.number().describe("Source issue ID"),
    issueToId: z.number().describe("Target issue ID"),
    relationType: z.enum([...]),
  }),
```

Relations accept two issue IDs in the same argument schema; if the arguments were reordered in a workflow invocation, the method would silently swap source and target.

### Project IDs vs. Project Identifiers

**Evidence**: Projects can be referenced by either numeric ID or string identifier (slug).

- `/redmine/extensions/models/redmine/redmine.ts:356–369` — globalArgs schema: `project: z.string().optional().describe("Default project identifier (omit for cross-project queries)")`
- `/redmine/extensions/models/redmine/redmine.ts:983–986` — `list_issues` uses `projectId` as the argument name but stores a string identifier:
```typescript
const projectId = args.project ?? context.globalArgs.project;
if (projectId) {
  params.project_id = projectId;
}
```
- `/redmine/extensions/models/redmine/redmine.ts:1519` — `/projects/${encodeURIComponent(project)}/versions.json` passes project as URI path segment.

**Non-obvious detail**: Redmine API accepts both numeric project IDs and string identifiers in most endpoints (e.g., `/projects/1/versions.json` and `/projects/my-project/versions.json` both work). The code uses string identifiers throughout (`project: string`) but never validates that a user doesn't accidentally pass a numeric project ID where a string is expected.

**Critical lookup pattern** (`/devops-measurement/extensions/models/devops-measurement/collect_redmine.ts:148`):
```typescript
const projectId = String(issue.project.id);  // Redmine API: number
const targetCrew = projectCrew(projectId);   // Crew mapping lookup keyed on string form
```

Project ID is fetched as a `number` from the API and immediately converted to string for lookup. The build lookup function (`collect_redmine.ts:106–128`) accepts a crew reference with mappings keyed on string project IDs. **No validation that numeric API IDs match the string keys** — if a user maps crew to project "1" but the API returns `{ project: { id: 2 } }`, no error is raised; the lookup just returns empty string and marks crew as unresolved.

### Tracker, Status, Priority IDs (Numeric, Always)

**Evidence**: These are consistently numeric IDs from the Redmine API.

- `/redmine/extensions/models/redmine/redmine.ts:72–77` — `RawStatus`, `RawTracker`, `RawPriority` all use `id: number`.
- `/redmine/extensions/models/redmine/redmine.ts:947–955` — `list_issues` arguments:
```typescript
trackerId: z.number().optional().describe("Filter by tracker ID"),
statusId: z.union([
  z.number(),
  z.literal("open"),
  z.literal("closed"),
  z.literal("*"),
]).optional().describe("Filter by status ID or open/closed/*"),
```

**Non-obvious pattern**: `statusId` accepts a union of `number | "open" | "closed" | "*"`. The "open"/"closed"/"*" literals are Redmine API magic strings that filter by the `is_closed` flag, not actual status IDs. This means the same argument can mean two different things:
- `statusId: 5` → filter by numeric status ID 5
- `statusId: "open"` → filter by `is_closed=false` (all statuses marked not closed)

**No type-level enforcement of which contexts accept which values.**

### Pagination

**Evidence**: Offset/limit/total_count pagination with bounded fetches.

- `/redmine/extensions/models/redmine/_lib/api.ts:111–183` — `redmineApiPaginated`:
```typescript
export async function redmineApiPaginated&lt;T&gt;(
  host: string,
  apiKey: string,
  path: string,
  resultKey: string,
  params?: Record&lt;string, string&gt;,
  maxItems?: number,
  username?: string,
): Promise&lt;T[]&gt; {
  const cap = Math.min(maxItems ?? 100, 500);
  const pageSize = Math.min(cap, 100);
  const allResults: T[] = [];
  let offset = 0;

  while (allResults.length &lt; cap) {
    const queryParams = new URLSearchParams({
      ...params,
      offset: String(offset),
      limit: String(pageSize),
    });
    // ... fetch loop ...
    const totalCount: number = data.total_count ?? 0;
    allResults.push(...items);
    offset += items.length;
    if (offset &gt;= totalCount || items.length === 0) break;
  }
  return allResults.slice(0, cap);
}
```

**Pattern**: 
- Default `maxItems` is 100, capped at 500.
- Page size is `min(cap, 100)` — Redmine page size is hard-capped at 100.
- Loop stops when `offset &gt;= totalCount || items.length === 0`.
- Results are trimmed to `cap` before returning.

**No `truncated` flag**: The resource schemas do not carry a boolean indicating whether more results exist. A workflow cannot distinguish "I fetched all 50 issues" from "I fetched 50 issues but there are 5000 total and I gave up at the cap." Example:

- `/redmine/extensions/models/redmine/redmine.ts:376–420` — `issues` resource schema includes `totalCount: z.number()` but no `truncated` field.

**This is a data integrity bug**: If a workflow iterates over issues and assumes it has the full list because `totalCount` matches the fetch count, it will miss paginated results beyond the cap.
