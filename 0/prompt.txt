### [MEDIUM] Release notes and READMEs understate the vault requirement: every method of the model now needs a vault
**File:** `scripts/cloudflare-codegen/lib/extension_generator.ts` **Line(s):** 176; `scripts/snyk-codegen/lib/extension_generator.ts` 175; `scripts/griptape-codegen/lib/extension_generator.ts` 179; `scripts/falai-codegen/lib/extension_generator.ts` 145. **Issue:** swamp's `method_execution_service.ts:887` rejects any method whose kind counts as mutating (`isMutatingKind`) when *any* resource of the model has a sensitive field. `inferMethodKind` only recognises the exact names `get`/`list`/…. No generated method sets `kind`, so names like `list_projects` count as mutating. The docs say otherwise:
- cloudflare: "Such a method now needs a vault"
- snyk: "Create a vault before running a … method that creates or rotates a credential"
- griptape: "fail unless a vault exists when a response carries the value"
- falai: "`create_api_key` now requires a vault"

Datadog's notes are the only accurate ones ("refuses to run any of its methods, reads included").
**Breaking input:** a user with no vault who relies on the kept `CLOUDFLARE_API_TOKEN` fallback runs `list_projects` (cloudflare/pages, which is marked only because of `web_analytics_token`). Every cloudflare model in the "Secrets" tables behaves the same way: access, stream, logpush, r2, turnstile, tunnel, magic-transit, workers-ai, workers-scripts. So do snyk/apps, snyk/service-accounts, griptape/data-connectors and falai/keys, including their list and delete methods.
**Impact:** methods that previously worked now fail after upgrade, and the notes don't tell users.
**Fix:** either emit `kind: "list"`/`"read"` on generated list and get methods (the data writer still requires a vault for an actual sensitive write), or reword all four templates and the regenerated notes to match datadog's.

### [MEDIUM] Newly working Turnstile and Tunnel secret writers all write instance `"created"`, so each call overwrites the previous secret in the vault
**File:** `scripts/cloudflare-codegen/lib/method_classifier.ts` **Line(s):** 1064 (create body); output in `cloudflare/turnstile/.../turnstile.ts:366-369, 526-529` and `cloudflare/tunnel/.../tunnel.ts:806-814`
**Issue:** the create body names the instance `result.id ?? "created"`. Turnstile widgets have no `id` (their key is `sitekey`), and the tunnel management token is a bare string. These methods always failed before; the release notes now say they are fixed. In practice every call lands on `create/created`, `rotate_secret/created` or `a_cloudflare_tunnel_management_token/created`. The vault key is built from the instance name, so the stored secret is replaced.
**Breaking input:** run `get_create` for widget A, then for widget B. A's `secret` reference now resolves to B's secret. The same happens with `get_a_cloudflare_tunnel_management_token` across two tunnels.
**Impact:** this breaks the CLAUDE.md rule for collision-resistant instance names, in code this change made reachable. The values can be re-fetched, but stored references silently point at the wrong credential.
**Fix:** fall back to the last path parameter or a hash of the args (as falai and griptape do) instead of `"created"`.
