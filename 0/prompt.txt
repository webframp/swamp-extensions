## Findings

**MEDIUM: the API key and `X-Redmine-Username` go to whatever host a redirect points at**
- **Where:** `redmine/extensions/models/redmine/_lib/api.ts:37`, called by `redmineDownload` at about line 215, with the path built at `redmine.ts:2542`.
- **Evidence:** `fetch` follows redirects by default and only strips `Authorization` when the redirect changes origin, not custom headers. I tested this with Deno 2.9.7: a request to server A carrying `X-Redmine-API-Key: SECRET` got a 302 to `localhost:&lt;B&gt;`, and server B received `SECRET`.
- **Hostile intent: none.** The code reuses the existing `fetchWithRetry`, which `redmineApi` and `redmineApiPaginated` already use, so the same leak is on `main` today.
- **Why it's worse here:** attachment downloads are the endpoint where redirects actually happen in practice, such as storage plugins that redirect to S3 or a CDN, or proxies.
- **Fix:** set `redirect: "manual"` (or `"error"`) in `fetchWithRetry`, or follow redirects only when they stay on the same origin as `host`.
- **Decision needed:** the defect shares a root cause with the new code. Should it be fixed in this PR for all three helpers, or for the download path only?

**LOW: attachment fields from Redmine are not validated before files are written**
- **Where:** `redmine.ts:253-265` (`mapAttachments`), `redmine.ts:2558` (`createFileWriter`).
- **Evidence:** `a.id` from the response goes unchecked into the data name `attachment-&lt;issueId&gt;-&lt;id&gt;` and into the download path. The Zod resource schema only runs at the final `writeResource`, after the files are already stored.
- **Mitigations:** swamp's `DataMetadataSchema` rejects `..`, `/`, `\` and NUL in data names (`/home/sme/src/swamp-club/swamp/src/domain/data/data_metadata.ts:207-215`). The URL is always `${host}/attachments/...`, so a bad ID cannot change the host. The Redmine filename is never used as a path; it only appears in error messages.
- **Hardening option:** check that `a.id` is a positive integer in `mapAttachments`.
