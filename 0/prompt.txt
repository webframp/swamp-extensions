### [HIGH] `bump --update-sha` (cloudflare) and `bump --update-spec` (falai) can move the pin, regenerate nothing, and exit 0
**File:** `/home/sme/src/webframp/swamp-extensions/.worktrees/fix-pr513-open-questions/scripts/cloudflare-codegen/bump.ts` (`detectChanges`, and the re-exec in `main`); `/home/sme/src/webframp/swamp-extensions/.worktrees/fix-pr513-open-questions/scripts/falai-codegen/lib/bump.ts` (same structure)
**Issue:** After rewriting the pin, both tools re-run themselves without the pin flag. The child selects services only by `hasChanges: isNew || methods.length !== oldMethods`, so it detects changes by method count alone. A schema change that keeps the method count is invisible to it. The comment on `requireNotesForRepin` promises "a run never leaves it moved with nothing regenerated", and that promise does not hold.
**Breaking input:** An upstream commit adds or changes a property in the D1 export response without adding an operation. `deno task bump -- --update-sha --notes "x"` then:
1. rewrites `SCHEMA_SHA`/`SPEC_SHA256`,
2. re-runs the tool, which prints "No changes detected",
3. exits 0.

`d1.ts` is still built from the old spec. The next `generate:dry-run` reports d1 as changed, and that drift is then unrelated to whatever change triggers it. When some services do change count, only those are passed to `--services`; other services whose schemas changed are skipped.
**Impact:** Round-1 fix #2 (re-pin then regenerate from the new spec) is only partly achieved. The pin and the committed output can disagree with a success exit code.
**Fix:** After a re-pin, have the child run `main.ts` over all services without `--version`, so `computeModelVersion` decides by content, and forward `notesArgs`. Better still, drop the method-count prefilter in favour of main.ts's content-based detection.
