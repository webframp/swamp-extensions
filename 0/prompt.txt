### [LOW] The pin is restored even when `main.ts` already rewrote some extensions from the new spec
**File:** `scripts/cloudflare-codegen/bump.ts`, `scripts/falai-codegen/lib/bump.ts`
**Line(s):** cloudflare 221-224; falai 237-241
**Issue:** The restore runs on any non-zero exit from the child. `main.ts` can fail partway through its write pass, after some extensions are already written. A write error throws; a `deno fmt` failure only warns.
**Breaking input:** Any later extension has a read-only file, or the disk fills. I reproduced it with `chmod 444 models/README.md` plus changes in `threads` and `models`. The run exited 1 with "Permission denied" on `models/README.md`, after `threads` had already been rewritten with a new version and new notes. Under `bump --update-sha` or `--update-spec`, `config.ts` and the vendored spec would then go back to the old pin.
**Impact:** The tree is left inconsistent: some extensions are generated from the new spec and bumped, but the pin points at the old spec. The message "restored the previous pin" suggests nothing changed. Those files are also left unformatted. Git can recover it, and the trigger is rare. Ctrl-C has a related gap: it kills the parent process without restoring anything.
**Fix:** Restore only when the child failed before it wrote anything. For example, `main.ts` could exit with a distinct code for refusals before the write pass, and the parent restores only on that code. Otherwise, print the list of directories that were already written so the user can revert them.
